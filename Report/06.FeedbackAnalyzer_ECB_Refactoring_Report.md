# Feedback Analyzer ECB 리팩토링 수행 보고서

## 1. 보고서 개요

본 보고서는 `src/cpp` 코드 전반에 대해 수행한 ECB(Entity-Control-Boundary) 관점의 리팩토링 내용을 정리한다.

이번 작업의 목적은 `main.cpp`에 집중되어 있던 HTTP 라우팅, 입력 파싱, 분석 흐름, 출력 생성 책임을 분리하고, 기존 Golden Master 및 감정 분석 테스트가 모두 통과하는 상태에서 구조 개선을 완료하는 것이다.

## 3. 리팩토링 전 주요 문제

| 대상 | 문제 | 영향 |
| --- | --- | --- |
| `main.cpp` | 서버 초기화, 라우팅, 파싱, 검증, 분석, 응답 생성이 한 파일에 혼재 | SRP 위반, 변경 영향 범위 증가 |
| `main.cpp` 전역 상태 | `fil_data`, `textAnalyzer`, `filters`가 파일 전역으로 존재 | 상태 소유권 불명확 |
| `/analyze` 핸들러 | form 파싱, trim, 저장, 분석, 로깅, HTML 응답 생성이 혼재 | 테스트와 재사용이 어려움 |
| `/upload` 핸들러 | HTTP 파일 접근, CSV 파싱, 상태 변경, 응답 생성이 혼재 | Boundary와 Control 책임 혼재 |
| `/filter` 핸들러 | 필터링, 결과 저장, 재분석, 오류 응답이 혼재 | 분기 증가, OCP 위반 가능성 |
| `TextAnalyzer.h` | 분석 구현이 헤더에 인라인으로 존재 | 컴파일 의존성 증가, 구현 노출 |
| `Filters.h` | 필터 구현과 `else if` 감정 판별 체인이 헤더에 존재 | 확장 시 기존 코드 수정 필요 |
| `Logger.h`, `Session.h` | 구현이 헤더에 인라인으로 존재 | 책임 경계 불명확 |
| `FileHandler.h` | 실제 사용처가 없는 죽은 코드 | 유지보수 비용 증가 |

## 4. ECB 분리 결과

### 4.1 Entity / Domain

| 파일 | 역할 |
| --- | --- |
| `Feedback.h` | 피드백 텍스트 값 보관 |
| `TextAnalyzer.h/.cpp` | 감정/키워드 분석 규칙 |
| `Filters.h/.cpp` | 피드백 감정/키워드 필터링 |
| `Constants.h/.cpp` | 감정 및 카테고리 키워드 사전 |

### 4.2 Control

| 파일 | 역할 |
| --- | --- |
| `ApplicationContext.h/.cpp` | 앱 초기화와 핵심 의존성 보유 |
| `FeedbackController.h/.cpp` | analyze, upload, filter, download 유스케이스 흐름 조합 |

### 4.3 Boundary

| 파일 | 역할 |
| --- | --- |
| `FeedbackServer.h/.cpp` | `httplib` 라우팅과 HTTP 응답 연결 |
| `FormParser.h/.cpp` | form body 파싱 및 URL decode |
| `CsvParser.h/.cpp` | CSV 입력 파싱 |
| `CsvExporter.h/.cpp` | CSV 출력 생성 |
| `HtmlRenderer.h/.cpp` | HTML 응답 생성 |

## 5. 주요 변경 내용

### 5.1 `main.cpp` 축소

리팩토링 후 `main.cpp`는 앱 조립과 실행만 담당한다.

```cpp
int main() {
    ApplicationContext app;
    app.init();

    FeedbackServer server(app);
    if (!server.run("0.0.0.0", 8080)) {
        Logger::logError(u8"서버 시작에 실패했습니다.");
        return 1;
    }

    return 0;
}
```

### 5.2 HTTP 라우팅 분리

`FeedbackServer`가 `httplib::Server`를 보유하고 `/`, `/analyze`, `/upload`, `/filter`, `/download` 라우트를 등록하도록 분리했다.

이로써 `main.cpp`는 `httplib` 세부 API에 직접 의존하지 않는다.

### 5.3 유스케이스 흐름 분리

`FeedbackController`는 다음 책임을 가진다.

| 메서드 | 책임 |
| --- | --- |
| `home()` | 초기 화면 HTML 생성 |
| `analyze()` | 입력 텍스트 정규화, 피드백 추가, 분석 실행 |
| `upload()` | CSV 입력을 피드백 목록으로 변환 후 저장 |
| `filter()` | 감정/키워드 필터링 및 분석 결과 생성 |
| `downloadCsv()` | 필터링 결과 CSV 출력 생성 |

### 5.4 Boundary 유틸 분리

`main.cpp`에 있던 form 파싱, CSV 파싱, CSV 출력, HTML 렌더링 코드를 각각 별도 모듈로 이동했다.

| 기존 위치 | 신규 위치 |
| --- | --- |
| `urlDecode()`, `parseForm()` | `FormParser` |
| `parseCsvLine()` 및 업로드 CSV 처리 | `CsvParser` |
| 다운로드 CSV 문자열 생성 | `CsvExporter` |
| `renderPage()`, HTML escape, timestamp | `HtmlRenderer` |

### 5.5 Domain 구현 정리

`TextAnalyzer`와 `Filters`의 헤더 인라인 구현을 `.cpp`로 이동했다.

`Filters`의 감정 판별은 `else if` 체인 대신 우선순위 목록 순회 방식으로 변경했다.

```cpp
for (const auto& sentiment : priority) {
    if (containsAny(text, S_KEYWORDS[sentiment])) {
        return sentiment;
    }
}
```

### 5.6 Dead Code 제거

사용되지 않던 `FileHandler.h`를 제거했다.

`Session`의 미사용 private 상태인 `internalData`, `filterOptions`도 제거했다.

## 7. 커버리지 확인

이전 커버리지 확인에서 `build-gcov`와 `lcov`를 사용해 다음 결과를 확인했다.

| 영역 | 기준 | 결과 |
| --- | --- | --- |
| Domain 후보 `TextAnalyzer.cpp`, `Constants.cpp` 라인 커버리지 | 95% 이상 | 96.1% |
| Boundary 후보 `main.cpp` 라인 커버리지 | 85% 이상 | 0.0% |

Boundary 커버리지는 당시 `main.cpp`가 HTTP 서버 런타임 중심이라 직접 테스트되지 않아 기준을 충족하지 못했다.

이번 리팩토링으로 Boundary 책임이 `FormParser`, `CsvParser`, `CsvExporter`, `HtmlRenderer`, `FeedbackServer`로 분리되었으므로, 다음 단계에서는 이 모듈별 단위 테스트를 추가해 Boundary 커버리지를 올릴 수 있다.

## 10. 결론

이번 리팩토링으로 `main.cpp`의 책임은 앱 조립과 서버 실행으로 축소되었다.

HTTP Boundary, 유스케이스 Control, 분석/필터 Domain이 명확히 분리되었고, 기존 61개 테스트와 Approval Golden Master 테스트가 모두 통과해 출력 계약이 유지됨을 확인했다.

다음 단계는 새로 분리된 Boundary 및 Controller 모듈에 테스트를 추가해 Boundary 커버리지 기준을 충족시키는 것이다.
