# Feedback Analyzer 리팩터링 설계 보고서

## 1. 보고서 목적

이 보고서는 고객 피드백 분석 시스템의 문제 정의, 학습 맥락, Boundary-Control-Entity 설계 방향, TDD 규칙, 프로젝트 규칙, README To-Do List를 하나의 기준 문서로 정리한다.

대상 프로젝트는 C++17 이상을 기준으로 하며, 자연어 기반 고객 피드백을 수집, 분류, 분석, 시각화하는 웹 애플리케이션이다. 현재 프로젝트는 리팩터링 챌린지 성격을 가지며, 의도적으로 긴 함수, 중복 로직, 전역 상태, 하드코딩, 테스트 미비, 책임 혼재 같은 코드 스멜을 포함한다.

## 2. 문제 정의 요약

고객 피드백 분석의 핵심 문제는 단순히 텍스트를 감정과 카테고리로 분류하는 것이 아니다. 변화하는 분석 규칙을 안정적인 계약 안에서 다루고, 동일한 입력에 대해 일관된 결과를 제공하며, 출력 형식을 테스트 가능한 계약으로 유지하는 것이다.

고객 피드백은 제품 개선의 우선순위를 정하는 근거가 된다. 따라서 분석 기준이 불명확하거나 실행 시점마다 결과가 달라지면 잘못된 의사결정으로 이어질 수 있다. 이 프로젝트는 피드백 분석 기능을 통해 OCP, SRP, 입력 검증, 설정 외부화, 동적 분석 단위 등록, 출력 포맷 고정을 학습한다.

## 3. 핵심 Invariant

- 동일한 유효 입력은 동일한 분석 결과를 생성해야 한다.
- 유효하지 않은 입력은 분석 단계로 넘어가기 전에 식별되어야 한다.
- 새로운 분석 단위가 추가되어도 기존 분석 결과의 필드 의미는 바뀌지 않아야 한다.
- 분류, 감정, 키워드 기준의 변경은 출력 계약을 깨뜨리지 않아야 한다.
- 출력 포맷은 테스트로 검증 가능한 고정 구조를 가져야 한다.

## 4. Boundary-Control-Entity 설계 방향

### 4.1 Boundary

Boundary는 외부 입력 수신, 입력 검증, 출력 변환, 오류 응답 생성을 담당한다. HTTP, CSV, HTML, JSON 같은 외부 표현은 Boundary의 책임이다.

Boundary는 도메인 규칙을 직접 판단하지 않는다. 또한 Entity 내부 상태를 직접 수정하지 않는다.

### 4.2 Control

Control은 유스케이스 흐름을 조정한다. Boundary 요청을 받아 필요한 규칙과 데이터를 준비하고, Entity 작업을 호출한 뒤 결과를 Boundary가 출력할 수 있는 형태로 전달한다.

Control은 출력 포맷을 만들지 않는다. 출력 포맷은 Boundary 책임으로 남긴다.

### 4.3 Entity

Entity는 도메인 규칙, 불변식, 분석 결과의 의미를 담당한다. 감정 라벨, 카테고리 라벨, 피드백 텍스트, 분석 결과, 분석 요약 같은 개념이 Entity에 속한다.

Entity는 HTTP, CSV, 파일 시스템, UI를 알지 않는다.

### 4.4 의존성 방향

의존성 방향은 다음 기준으로 고정한다.

- Boundary -> Control
- Control -> Entity
- Control -> Data Interface
- Data Implementation -> Data Interface
- Entity는 Boundary, Control, Data Implementation에 의존하지 않는다.

## 5. Domain 설계 요약

### 5.1 주요 개념

- FeedbackText: 단일 고객 피드백 원문과 텍스트 유효성 규칙을 표현한다.
- FeedbackId: 피드백 식별자와 분석 결과 매핑을 책임진다.
- SentimentLabel: 긍정, 부정, 중립 중 하나의 감정 결과를 표현한다.
- CategoryLabel: 배송, 가격, 품질, 서비스 등 분류 결과를 표현한다.
- KeywordRule: 키워드와 감정 또는 카테고리 연결 규칙을 표현한다.
- AnalysisUnit: 독립 실행 가능한 분석 단위를 표현한다.
- AnalysisResult: 단일 피드백의 분석 결과를 표현한다.
- AnalysisSummary: 여러 피드백의 집계 결과를 표현한다.

### 5.2 대표 유스케이스

- 단일 피드백 분석
- 다중 피드백 분석
- 감정별 필터링
- 카테고리별 필터링
- 분석 단위 등록
- 분석 규칙 교체

## 6. Boundary 계약 요약

### 6.1 입력 흐름

입력 흐름은 입력, 검증, 실행, 출력 순서로 고정한다.

- 입력: 사용자는 단일 텍스트 또는 CSV 텍스트 컬럼을 제출한다.
- 검증: Boundary는 필수 필드, 타입, 길이, 행 개수, 인코딩 가능 여부를 검증한다.
- 실행: Control은 검증된 요청을 Domain 유스케이스에 전달한다.
- 출력: Boundary는 Domain 결과를 고정된 출력 스키마로 변환한다.
- 실패: Boundary는 BoundaryError, DomainError, DataError를 고정된 오류 스키마로 변환한다.

### 6.2 에러 메시지 패턴

- 필수 필드 누락: `필수 필드가 누락되었습니다: {field}`
- 타입 오류: `필드 타입이 올바르지 않습니다: {field}, expected={type}`
- 빈 값 오류: `빈 값은 허용되지 않습니다: {field}`
- 길이 초과: `허용 길이를 초과했습니다: {field}, max={max}`
- 범위 오류: `허용되지 않는 값입니다: {field}, allowed={allowedValues}`
- 중복 오류: `중복 값은 허용되지 않습니다: {field}`
- 도메인 규칙 오류: `도메인 규칙을 위반했습니다: {ruleId}`
- 내부 변환 오류: `출력 변환에 실패했습니다: {contractName}`

## 7. Data 설계 요약

Data 레이어는 분석 규칙과 분석 단위 설정을 Domain 밖에서 공급한다. Data 레이어는 피드백 의미를 해석하지 않으며, 저장 형식, 읽기, 쓰기, 로딩 실패, 스키마 검증만 책임진다.

권장 방식은 File 기반 설정이다. 감정 키워드, 카테고리, 분석 단위 설정을 코드 밖에서 변경할 수 있고, 하드코딩 제거와 설정 외부화라는 학습 목표에 직접 연결되기 때문이다.

테스트에서는 InMemory 구현을 사용하고, 통합 테스트에서는 File 기반 구현을 사용한다.

## 8. TDD 및 테스트 기준

### 8.1 TDD 단계

- Red: 실패하는 테스트를 먼저 작성하여 기대 동작과 계약을 고정한다.
- Green: 실패 테스트를 통과시키는 최소 구현만 수행한다.
- Refactor: 모든 테스트가 통과한 뒤 동작을 유지하며 구조를 개선한다.

### 8.2 테스트 도구

- 단위 테스트: Google Test
- 출력 승인 테스트: Approval Tests
- 테스트 구조: Given-When-Then 주석 구조

### 8.3 커버리지 목표

- Domain 라인 커버리지: 95%
- Domain 분기 커버리지: 90%
- Boundary 라인 커버리지: 90%
- Data 라인 커버리지: 85%
- 계약 테스트: 100% 통과

## 9. 금지 규칙

- `std::cout` 또는 `std::cerr` 디버그 출력을 남발하지 않는다.
- 매직 넘버와 매직 문자열을 하드코딩하지 않는다.
- `catch(...)`를 무분별하게 사용하지 않는다.
- 헤더 파일에 일반 함수 또는 클래스 메서드 구현을 포함하지 않는다.
- 전역 mutable 상태를 남용하지 않는다.
- 헤더에 `using namespace std`를 작성하지 않는다.
- raw pointer 소유권을 명확한 규칙 없이 사용하지 않는다.
- `new`와 `delete`를 직접 짝지어 자원 수명을 관리하지 않는다.
- 테스트를 통과시키기 위해 프로덕션 계약을 완화하지 않는다.
- 레이어를 우회하여 Boundary에서 Entity 내부 규칙을 직접 수정하지 않는다.

## 11. 통합 검증 시나리오

### 11.1 정상 시나리오

- 단일 부정 피드백을 제출하면 분석 결과의 감정이 부정이다.
- CSV 배치 입력 3건을 제출하면 집계 totalCount가 3이다.
- 배송 키워드가 포함된 입력은 카테고리에 배송을 포함한다.
- 감정 필터가 부정이면 결과 목록에는 부정 결과만 포함된다.

### 11.2 실패 시나리오

- text 필드가 없으면 Domain을 호출하지 않고 오류 응답을 반환한다.
- text가 공백이면 오류 응답의 field가 `items.text`다.
- items가 501개이면 길이 제한 오류 응답을 반환한다.
- 설정 파일에 중복 감정 키워드가 있으면 실행 전 DataError를 반환한다.
- Domain이 등록되지 않은 카테고리를 반환하면 Boundary는 도메인 규칙 오류로 변환한다.

## 13. 결론

이 프로젝트의 리팩터링 목표는 기능을 많이 추가하는 것이 아니라, 고객 피드백 분석 규칙을 안정적인 계약 안에서 변경 가능하게 만드는 것이다. 이를 위해 BCE 의존성 방향을 고정하고, TDD를 통해 계약을 먼저 보호하며, 출력 포맷은 Approval Test로 회귀를 방지해야 한다.

우선순위는 테스트 기반 보호막 구축, Boundary-Control-Entity 책임 분리, 하드코딩 및 전역 상태 제거, 출력 계약 고정 순서로 진행한다.
