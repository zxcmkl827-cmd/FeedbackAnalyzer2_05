위의 분석된 코드들을 ECB(Entity-Control-Boundary) 패턴으로 분석해줘.
코드는 수정하지 말고 다음만 답해줘:

1. 현재 main() 함수에서 ECB 역할이 어떻게 혼재하는가?
   - Entity: ###
   - Control: ###
   - Boundary: ###
의 형태로 정리해줘
2. 어느 코드를 어느 클래스/모듈로 이동해야 하는가?
3. 새 단위 추가 시 변경이 최소화되는 구조를 제안하라.


---

**Cursor**

1. 현재 `main()`의 ECB 혼재

- Entity: `Feedback`, `feedbacks`, `fil_data`, `sentimentResults`, `keywordResults` 같은 도메인 데이터와 상태가 `main()` 흐름 안에서 직접 생성·수정됩니다.
- Control: `/analyze`, `/upload`, `/filter`, `/download` 핸들러 안에서 입력 검증, 피드백 추가, 분석 실행, 필터링, 로그 기록, 결과 선택까지 유스케이스 로직이 직접 수행됩니다.
- Boundary: `httplib::Server`, `Request/Response`, `renderPage()`, `parseForm()`, `parseCsvLine()`, CSV 다운로드 응답, HTML 생성이 모두 `main.cpp`에 붙어 있어 외부 입출력 책임도 섞여 있습니다.

2. 이동 제안

- `Feedback`, 현재 피드백 목록, 필터링 결과 상태  
  → `FeedbackRepository`, `SessionStore`, `FeedbackStore` 같은 Entity/저장소 모듈로 이동

- `/analyze`의 텍스트 trim, `Feedback` 생성, 분석 호출 흐름  
  → `AnalyzeFeedbackUseCase` 또는 `FeedbackAnalysisController`

- `/upload`의 CSV 파일 처리, 행 파싱, 피드백 생성  
  → `CsvFeedbackImporter` + `UploadFeedbackUseCase`

- `/filter`의 감정/키워드 필터 적용과 결과 분석  
  → `FilterFeedbackUseCase` 또는 `FeedbackFilterController`

- `renderPage()`의 HTML 생성  
  → `HtmlRenderer` 또는 `FeedbackPageView`

- `parseForm()`, `urlDecode()`  
  → `FormParser` 또는 HTTP Boundary 유틸

- `parseCsvLine()`과 `/download` CSV 생성  
  → `CsvParser`, `CsvExporter`

- `TextAnalyzer::sent()`, `TextAnalyzer::kw()`  
  → `SentimentAnalyzer`, `KeywordAnalyzer`로 분리

- `Filters::fil()`  
  → 콘솔 출력 제거 후 `FeedbackFilterService` 같은 Control/Domain Service로 이동

- `Constants::init()`의 키워드 데이터  
  → `KeywordCatalog`, `SentimentDictionary`, `CategoryDictionary`처럼 데이터 제공 역할로 분리

3. 새 단위 추가 시 변경 최소화 구조

감정/카테고리 같은 “새 단위”는 `if-else`에 추가하지 않고, `KeywordCatalog`에 데이터로 등록하고 `Analyzer`/`Filter`는 공통 인터페이스로 순회하게 만드는 구조가 좋습니다.

예상 구조는 `main()`이 서버 실행과 의존성 조립만 담당하고, HTTP 요청은 Boundary, 유스케이스 흐름은 Control, `Feedback`과 키워드 사전은 Entity/Domain Data로 분리하는 방식입니다. 그러면 새 감정이나 카테고리를 추가할 때 `main.cpp`, 라우터, 필터 조건문을 수정하지 않고 키워드 사전 또는 전략 클래스만 추가하면 됩니다.
