## STEP 1 — Observation

### 1) 상황 관찰

우리는 고객이 남긴 자연어 피드백을 수집하고, 감정·키워드·분류 기준에 따라 해석해 결과로 보여주는 시스템을 다루고 있다. 현재 관심사는 “분석 기능을 어떻게 구현할 것인가”보다, 변화하는 피드백 기준과 출력 요구를 안정적으로 수용하려면 무엇을 문제로 정의해야 하는가에 있다. 즉, 고객 피드백 분석은 단순 기능 구현 과제가 아니라 입력, 규칙, 분석 단위, 출력 계약을 명확히 분리하고 검증 가능한 구조로 만드는 리팩토링 학습 상황이다.

### 2) 왜 고객 피드백 분석 문제를 다루는가?

고객 피드백은 제품의 문제, 기대, 불만, 만족 신호가 직접 드러나는 데이터다. 그러나 자연어 피드백은 표현이 다양하고, 감정·카테고리·키워드 기준이 자주 바뀌며, 분석 결과가 의사결정에 사용되기 때문에 일관성과 재현성이 중요하다. 그래서 이 문제는 “작동하는 기능”을 넘어서 “변경 가능한 규칙을 어떻게 안전하게 다룰 것인가”를 훈련하기에 적합하다.

### 3) 학습 맥락

이 문제는 OCP/SRP, 입력 검증, 설정 외부화, 동적 단위 등록, 출력 포맷 고정이라는 설계 학습 맥락에서 등장한다. 감정 기준이나 카테고리가 늘어날 때 기존 흐름을 계속 수정해야 한다면 OCP가 깨진 것이고, 분석·저장·렌더링·필터링 책임이 섞여 있다면 SRP가 깨진 것이다. 또한 잘못된 입력을 분석 로직 안에서 뒤늦게 처리하면 결과 신뢰도가 낮아지고, 키워드나 분류 규칙이 코드 내부에 박혀 있으면 변경 비용이 커진다. 따라서 이 과제의 핵심은 분석 알고리즘 자체보다, 변경 가능한 규칙과 고정되어야 할 계약을 구분하는 사고를 훈련하는 데 있다.

## STEP 2 — Why #1: 고객의 피드백 결과가 왜 중요한가?

고객 피드백 결과는 제품 개선의 우선순위를 정하는 근거가 된다. 단순히 “긍정이 많다” 또는 “부정이 많다”를 보는 것이 아니라, 어떤 문제 영역에서 불만이 반복되는지, 어떤 요구가 새롭게 나타나는지, 어느 기준으로 고객 경험을 해석할지 결정하게 해준다.

따라서 분석 결과가 불안정하거나 기준이 불명확하면 잘못된 의사결정으로 이어질 수 있다. 같은 입력이 실행 시점이나 규칙 위치에 따라 다르게 해석된다면, 결과는 데이터가 아니라 우연한 출력에 가깝다. 고객 피드백 분석에서 중요한 것은 더 복잡한 기능이 아니라, 해석 기준의 일관성과 변경 가능성이다.

## STEP 3 — Why #2: 수동이 아닌 프로그램(+테스트)인 이유?

수동 분석은 소량의 피드백을 빠르게 이해하는 데는 유용하지만, 반복성·일관성·검증 가능성이 약하다. 분석자가 바뀌거나 기준이 조금 달라지면 같은 문장도 다른 결과로 분류될 수 있고, 기준 변경의 영향 범위를 추적하기 어렵다.

프로그램은 동일 입력에 대해 동일 결과를 내야 하며, 테스트는 그 약속이 깨지지 않았는지 확인하는 장치다. 특히 입력 검증, 분류 규칙, 감정 판단, 출력 포맷은 사람이 눈으로 확인하기보다 테스트로 고정해야 한다. 이 과제에서 테스트는 구현 보조 수단이 아니라, “분석 계약이 유지되고 있는가”를 확인하는 학습 도구다.

## STEP 4 — Why #3: 계약을 먼저 고정하려는 이유?

계약을 먼저 고정해야 변경 가능한 부분과 변경되면 안 되는 부분을 구분할 수 있다. 입력이 어떤 형태여야 하는지, 유효하지 않은 입력은 어떻게 처리되는지, 분석 결과는 어떤 필드를 가져야 하는지, 출력 포맷은 어떤 구조를 유지해야 하는지가 먼저 정해져야 한다.

계약이 없으면 리팩토링은 내부 구조 변경이 아니라 동작 변경이 될 위험이 크다. 반대로 계약이 고정되어 있으면 내부 구현, 분석 단위 등록 방식, 설정 관리 방식, 출력 생성 방식은 자유롭게 개선할 수 있다. 이것이 OCP와 SRP를 연습하기 전에 계약을 먼저 정의해야 하는 이유다.

## STEP 5 — 문제 정의

### 1) 표면 문제

고객 피드백을 감정과 카테고리 기준으로 분석하고 결과를 보여주는 기능이 필요하다. 현재 문제는 피드백 분석 기준과 출력 방식이 변경될 때 시스템이 쉽게 흔들린다는 점이다.

### 2) 개선된 정의

우리가 해결해야 할 문제는 고객 피드백을 일관된 계약에 따라 입력받고, 검증하고, 분석 단위별로 처리한 뒤, 고정된 출력 형식으로 제공하는 구조를 정의하는 것이다. 감정 기준, 키워드 기준, 카테고리 기준은 변경될 수 있으므로 코드 내부에 고정된 사실처럼 다루면 안 된다. 새로운 분석 단위가 추가되어도 기존 분석 흐름과 출력 계약이 깨지지 않아야 한다. 입력 검증은 분석 결과의 신뢰도를 지키는 선행 조건이어야 한다. 출력 포맷은 테스트 가능한 계약으로 유지되어야 하며, 내부 리팩토링과 독립적으로 보존되어야 한다. 이 문제의 본질은 “피드백을 분석한다”가 아니라 “변화하는 분석 규칙을 안정적인 계약 안에서 다룬다”이다.

### 3) 핵심 Invariant

- 동일한 유효 입력은 동일한 분석 결과를 생성해야 한다.
- 유효하지 않은 입력은 분석 단계로 넘어가기 전에 식별되어야 한다.
- 새로운 분석 단위가 추가되어도 기존 분석 결과의 필드 의미는 바뀌지 않아야 한다.
- 분류·감정·키워드 기준의 변경은 출력 계약을 깨뜨리지 않아야 한다.
- 출력 포맷은 테스트로 검증 가능한 고정 구조를 가져야 한다.

### 4) 훈련하려는 사고 능력

- 변경 가능한 정책과 고정되어야 할 계약을 분리하는 능력
- 책임을 기준으로 입력, 분석, 설정, 출력을 나누는 능력
- 테스트를 통해 리팩토링의 안전 범위를 정의하는 능력

## 전제

Dual-Track 기준은 다음처럼 고정한다.

- **Domain Track**: 피드백 의미 해석, 감정 판단, 카테고리 판단, 분석 결과 규칙을 담당한다.
- **UI/Boundary Track**: 입력 수신, 형식 검증, 에러 변환, 출력 포맷 고정을 담당한다.
- **BCE 기준**: Boundary는 외부 계약, Control은 유스케이스 실행 순서, Entity는 도메인 규칙과 불변식을 담당한다.

## 1) Entity(Domain) 설계

### 1.1 개념 목록과 SRP

- **FeedbackText**: 단일 고객 피드백 원문을 표현한다. 텍스트 공백, 길이, 비어 있음 여부 규칙만 책임진다.
- **FeedbackId**: 분석 대상 피드백의 식별자다. 중복 추적과 결과 매핑만 책임진다.
- **SentimentLabel**: 긍정, 부정, 중립 중 하나의 감정 결과를 표현한다.
- **CategoryLabel**: 배송, 가격, 품질, 서비스 등 분류 결과를 표현한다.
- **KeywordRule**: 특정 키워드가 어떤 감정 또는 카테고리에 연결되는지 표현한다.
- **AnalysisUnit**: 감정 분석, 카테고리 분석, 키워드 추출처럼 독립 실행 가능한 분석 단위를 표현한다.
- **AnalysisResult**: 단일 피드백의 분석 결과를 표현한다.
- **AnalysisSummary**: 여러 피드백의 집계 결과를 표현한다.

### 1.2 Invariants

- FeedbackText는 trim 이후 길이가 1 이상이어야 한다.
- FeedbackText는 trim 이후 길이가 1,000자 이하이어야 한다.
- SentimentLabel은 긍정, 부정, 중립 중 정확히 하나여야 한다.
- AnalysisResult는 입력 FeedbackId와 결과 FeedbackId가 동일해야 한다.
- AnalysisResult는 최소 1개의 SentimentLabel을 가져야 한다.
- CategoryLabel은 등록된 카테고리 목록 안에 존재해야 한다.
- AnalysisUnit의 이름은 등록 목록 안에서 중복될 수 없다.

### 1.3 유스케이스

- 단일 피드백 분석: 하나의 텍스트를 검증한 뒤 감정과 카테고리를 산출한다.
- 다중 피드백 분석: 여러 텍스트를 각각 분석하고 결과 목록과 집계를 산출한다.
- 감정별 필터링: 분석 결과 목록에서 지정 감정만 반환한다.
- 카테고리별 필터링: 분석 결과 목록에서 지정 카테고리만 반환한다.
- 분석 단위 등록: 새 분석 단위를 기존 분석 흐름에 추가한다.
- 분석 규칙 교체: 키워드 또는 카테고리 규칙을 외부 설정 기준으로 교체한다.

### 1.4 Domain API

본문 없이 시그니처 수준으로만 정의한다.

- `ValidateFeedbackText(rawText) -> FeedbackText | DomainError`
  - 실패 조건: null 입력, trim 후 빈 문자열, 최대 길이 초과
- `AnalyzeSingleFeedback(feedbackId, feedbackText, ruleSet) -> AnalysisResult | DomainError`
  - 실패 조건: 유효하지 않은 FeedbackId, 비어 있는 ruleSet, 등록되지 않은 카테고리 참조
- `AnalyzeFeedbackBatch(feedbackItems, ruleSet) -> AnalysisResultList | DomainError`
  - 실패 조건: 입력 목록 비어 있음, 중복 FeedbackId, 단일 항목 검증 실패
- `ClassifySentiment(feedbackText, sentimentRules) -> SentimentLabel | DomainError`
  - 실패 조건: 감정 규칙 비어 있음, 동일 키워드가 서로 다른 감정에 중복 등록
- `ClassifyCategory(feedbackText, categoryRules) -> CategoryLabelList | DomainError`
  - 실패 조건: 카테고리 규칙 비어 있음, 등록되지 않은 카테고리 반환
- `FilterBySentiment(results, sentimentLabel) -> AnalysisResultList | DomainError`
  - 실패 조건: 결과 목록 비어 있음, 존재하지 않는 감정 라벨
- `RegisterAnalysisUnit(unitName, unitContract) -> RegistrationResult | DomainError`
  - 실패 조건: unitName 빈 값, unitName 중복, unitContract 누락

### 1.5 Domain 단위 테스트 설계

RED 우선 테스트 목록이다.

- 빈 문자열 입력은 DomainError를 반환한다.
- 공백만 있는 입력은 DomainError를 반환한다.
- 1,001자 입력은 DomainError를 반환한다.
- 동일 입력과 동일 ruleSet은 동일 AnalysisResult를 반환한다.
- 부정 키워드만 포함된 입력은 부정 SentimentLabel을 반환한다.
- 긍정 키워드만 포함된 입력은 긍정 SentimentLabel을 반환한다.
- 감정 키워드가 없으면 중립 SentimentLabel을 반환한다.
- 배송 키워드가 포함되면 배송 CategoryLabel을 포함한다.
- 중복 FeedbackId가 포함된 배치 분석은 DomainError를 반환한다.
- 동일 이름의 AnalysisUnit 등록은 DomainError를 반환한다.

## 2) Boundary 설계

### 2.1 시나리오: 입력 → 검증 → 실행 → 출력

- 입력: 사용자는 단일 텍스트 또는 CSV 텍스트 컬럼을 제출한다.
- 검증: Boundary는 필수 필드 존재, 타입, 길이, 행 개수, 인코딩 가능 여부를 검증한다.
- 실행: Control은 검증된 요청을 Domain 유스케이스에 전달한다.
- 출력: Boundary는 Domain 결과를 고정된 Output schema로 변환한다.
- 실패: Boundary는 DomainError 또는 BoundaryError를 고정된 Error schema로 변환한다.

### 2.2 외부 계약

#### Input schema

- `requestId`: 필수, 문자열, trim 후 1자 이상
- `mode`: 필수, `single` 또는 `batch`
- `items`: 필수, 1개 이상 500개 이하
- `items.id`: 필수, 요청 안에서 유일한 문자열
- `items.text`: 필수, trim 후 1자 이상 1,000자 이하
- `filters.sentiment`: 선택, 값은 긍정·부정·중립 중 하나
- `filters.category`: 선택, 등록된 카테고리 이름

#### Output schema

- `requestId`: 입력 requestId와 동일
- `status`: `success`
- `results`: 분석 결과 목록
- `results.id`: 입력 item id와 동일
- `results.sentiment`: 긍정·부정·중립 중 하나
- `results.categories`: 0개 이상의 카테고리 목록
- `results.keywords`: 0개 이상의 매칭 키워드 목록
- `summary.totalCount`: results 개수와 동일
- `summary.sentimentCounts`: 감정별 개수 합이 totalCount와 동일
- `summary.categoryCounts`: 카테고리별 개수

#### Error schema

- `requestId`: 입력에서 식별 가능하면 동일 값, 불가능하면 `unknown`
- `status`: `error`
- `error.code`: 고정 에러 코드
- `error.message`: 고정 문구 패턴
- `error.field`: 실패 필드 경로
- `error.rejectedValue`: 보안상 허용된 경우에만 포함
- `error.details`: 동일 요청 안의 복수 오류 목록

### 2.3 Boundary 계약 테스트

Domain Mock을 가정한다.

- 정상 single 요청은 Domain의 단일 분석 유스케이스를 1회 호출한다.
- 정상 batch 요청은 Domain의 배치 분석 유스케이스를 1회 호출한다.
- items가 없으면 Domain을 호출하지 않고 Error schema를 반환한다.
- items.text가 빈 문자열이면 Domain을 호출하지 않고 Error schema를 반환한다.
- DomainError가 발생하면 Boundary는 Error schema로 변환한다.
- Domain 결과의 requestId는 입력 requestId로 유지된다.
- Output schema의 status는 성공 시 항상 `success`다.
- Error schema의 status는 실패 시 항상 `error`다.

### 2.4 에러 메시지 규칙

문구 패턴을 고정한다.

- 필수 필드 누락: `필수 필드가 누락되었습니다: {field}`
- 타입 오류: `필드 타입이 올바르지 않습니다: {field}, expected={type}`
- 빈 값 오류: `빈 값은 허용되지 않습니다: {field}`
- 길이 초과: `허용 길이를 초과했습니다: {field}, max={max}`
- 범위 오류: `허용되지 않는 값입니다: {field}, allowed={allowedValues}`
- 중복 오류: `중복 값은 허용되지 않습니다: {field}`
- 도메인 규칙 오류: `도메인 규칙을 위반했습니다: {ruleId}`
- 내부 변환 오류: `출력 변환에 실패했습니다: {contractName}`

## 3) Data 설계

### 3.1 목적

Data 레이어의 목적은 분석 규칙과 분석 단위 설정을 Domain 밖에서 공급하는 것이다. Data 레이어는 피드백 의미 해석을 하지 않는다. Data 레이어는 저장 형식, 읽기, 쓰기, 로딩 실패, 스키마 검증만 책임진다.

### 3.2 인터페이스 계약

이름만 제안한다.

- `RuleSetRepository`
- `CategoryRuleRepository`
- `SentimentRuleRepository`
- `AnalysisUnitRegistryStore`
- `FeedbackResultStore`
- `ConfigurationLoader`
- `ConfigurationValidator`

### 3.3 InMemory vs File 비교와 추천

#### InMemory

- 장점: 테스트가 빠르다.
- 장점: 외부 파일 손상 영향을 받지 않는다.
- 단점: 실행 종료 후 설정이 보존되지 않는다.
- 단점: 운영자가 규칙을 수정하려면 재빌드 또는 재시작 전략이 필요하다.

#### File(JSON/YAML)

- 장점: 감정 키워드, 카테고리, 분석 단위 설정을 코드 밖에서 변경할 수 있다.
- 장점: 변경 이력을 리뷰하기 쉽다.
- 장점: 학습 목표인 설정 외부화와 직접 연결된다.
- 단점: 파일 스키마 검증이 필요하다.
- 단점: 잘못된 파일이 로드되면 실행 전 실패 처리가 필요하다.

#### 추천

File 기반 설정을 추천한다. 이유는 이 과제의 핵심이 하드코딩 제거, 설정 외부화, 동적 분석 단위 등록이기 때문이다. 단위 테스트에는 InMemory 구현을 사용하고, 통합 테스트에는 File 기반 구현을 사용한다.

### 3.4 Data 레이어 테스트

- 유효한 감정 규칙 파일은 SentimentRule 목록으로 로드된다.
- 필수 필드가 누락된 규칙 파일은 DataError를 반환한다.
- 동일 키워드가 서로 다른 감정에 등록되면 DataError를 반환한다.
- 등록되지 않은 카테고리를 참조하는 규칙은 DataError를 반환한다.
- 빈 설정 파일은 DataError를 반환한다.
- 존재하지 않는 설정 파일은 DataError를 반환한다.
- 유효한 설정을 로드한 뒤 Domain ruleSet으로 변환할 수 있다.

## 4) Integration & Verification

### 4.1 의존성 방향 포함 흐름

의존성 방향은 다음으로 고정한다.

Boundary → Control → Domain ← Data Contract

- Boundary는 Domain Entity를 직접 생성하지 않는다.
- Boundary는 Control에 요청 DTO만 전달한다.
- Control은 Data에서 ruleSet을 가져온다.
- Control은 Domain 유스케이스를 호출한다.
- Domain은 Boundary와 Data 구현을 모른다.
- Data는 Domain이 요구하는 규칙 계약을 충족하는 값만 반환한다.
- 출력 변환은 Boundary에서만 수행한다.

### 4.2 통합 테스트 시나리오

#### 정상 시나리오

- 단일 부정 피드백을 제출하면 status가 success이고 sentiment가 부정이다.
- CSV 배치 입력 3건을 제출하면 summary.totalCount가 3이다.
- 배송 키워드가 포함된 입력은 categories에 배송을 포함한다.
- 감정 필터가 부정이면 results에는 부정 결과만 포함된다.

#### 실패 시나리오

- text 필드가 없으면 Domain을 호출하지 않고 Error schema를 반환한다.
- text가 공백이면 Error schema의 field가 `items.text`다.
- items가 501개이면 길이 제한 Error schema를 반환한다.
- 설정 파일에 중복 감정 키워드가 있으면 실행 전 DataError를 반환한다.
- Domain이 등록되지 않은 카테고리를 반환하면 Boundary는 도메인 규칙 오류로 변환한다.

### 4.3 회귀 보호 규칙

- Output schema의 필드명 변경은 계약 테스트 실패로 처리한다.
- Error message 패턴 변경은 계약 테스트 실패로 처리한다.
- SentimentLabel 값 집합 변경은 Domain 테스트 실패로 처리한다.
- 동일 입력의 결과가 달라지면 Domain 회귀 테스트 실패로 처리한다.
- 설정 파일 스키마 변경은 Data 계약 테스트 추가 없이는 허용하지 않는다.
- 새로운 AnalysisUnit 추가 시 기존 통합 테스트 결과가 변경되면 실패로 처리한다.

### 4.4 커버리지 목표

- Domain: 라인 커버리지 95% 이상, 분기 커버리지 90% 이상
- Boundary: 라인 커버리지 90% 이상, 계약 테스트 100% 통과
- Data: 라인 커버리지 85% 이상, 설정 실패 케이스 100% 포함
- Integration: 정상 2개 이상, 실패 3개 이상을 항상 실행
- Regression: 기존 공개 계약 테스트 100% 통과

### 4.5 Traceability Matrix

- **Concept: FeedbackText**
  - Rule: trim 후 1자 이상 1,000자 이하
  - UseCase: 단일 피드백 분석, 다중 피드백 분석
  - Contract: Input schema의 `items.text`
  - Test: 빈 문자열 거부, 길이 초과 거부
  - Component: Entity, Boundary

- **Concept: SentimentLabel**
  - Rule: 긍정·부정·중립 중 정확히 하나
  - UseCase: 감정 분석, 감정별 필터링
  - Contract: Output schema의 `results.sentiment`
  - Test: 감정 라벨 집합 검증, 필터 결과 검증
  - Component: Entity, Control

- **Concept: CategoryLabel**
  - Rule: 등록된 카테고리만 반환
  - UseCase: 카테고리 분석, 카테고리별 필터링
  - Contract: Output schema의 `results.categories`
  - Test: 등록 카테고리 반환, 미등록 카테고리 오류
  - Component: Entity, Data

- **Concept: KeywordRule**
  - Rule: 동일 키워드는 서로 다른 감정에 중복 등록 불가
  - UseCase: 규칙 로딩, 감정 분석
  - Contract: Data 설정 schema
  - Test: 중복 키워드 설정 거부
  - Component: Data, Entity

- **Concept: AnalysisUnit**
  - Rule: unitName은 등록 목록에서 유일
  - UseCase: 분석 단위 등록, 배치 분석
  - Contract: AnalysisUnit 등록 계약
  - Test: 중복 unitName 등록 거부
  - Component: Control, Entity

- **Concept: AnalysisResult**
  - Rule: 입력 id와 결과 id가 동일
  - UseCase: 분석 실행, 결과 출력
  - Contract: Output schema의 `results.id`
  - Test: request item id와 result id 매핑 검증
  - Component: Entity, Boundary

- **Concept: ErrorResponse**
  - Rule: 실패 시 status는 항상 `error`
  - UseCase: 입력 검증 실패, 도메인 실패, 데이터 실패
  - Contract: Error schema
  - Test: Boundary 에러 변환 계약 테스트
  - Component: Boundary, Control

project:
  language: "C++"
  standard: "C++17 이상"
  goal: "고객 피드백 분석 시스템을 테스트 가능한 Boundary-Control-Entity 구조로 유지한다."

code_style:
  formatter: "clang-format"
  naming:
    types: "PascalCase"
    functions: "camelCase"
    variables: "camelCase"
    constants: "kPascalCase"
    files:
      headers: "PascalCase.h"
      sources: "PascalCase.cpp"
      tests: "*Test.cpp"
  header_source_separation:
    - "헤더에는 선언만 둔다."
    - "구현은 소스 파일에 둔다."
    - "템플릿 또는 constexpr처럼 C++ 규칙상 필요한 경우만 헤더 구현을 허용한다."
    - "헤더는 include guard 또는 pragma once를 사용한다."
    - "헤더는 불필요한 include 대신 전방 선언을 우선한다."

architecture:
  layers:
    boundary:
      responsibility: "외부 입력 수신, 입력 검증, 출력 변환, 오류 응답 생성을 담당한다."
    control:
      responsibility: "유스케이스 흐름 조정, Boundary 요청을 Entity 작업으로 연결, 저장소 호출 순서를 담당한다."
    entity:
      responsibility: "도메인 규칙, 불변식, 분석 결과 의미를 담당한다."
  dependency_direction:
    - "boundary -> control"
    - "control -> entity"
    - "control -> data_interface"
    - "data_implementation -> data_interface"
    - "entity는 boundary, control, data_implementation에 의존하지 않는다."
  rules:
    - "Boundary는 도메인 규칙을 직접 판단하지 않는다."
    - "Control은 출력 포맷을 만들지 않는다."
    - "Entity는 HTTP, CSV, 파일 시스템, UI를 알지 않는다."
    - "레이어 간 전달 데이터는 명시적 계약으로 정의한다."

tdd_rules:
  red_phase:
    description: "실패하는 테스트를 먼저 작성하여 기대 동작과 계약을 고정한다."
    rules:
      - "프로덕션 코드 변경 전에 실패 테스트를 먼저 작성한다."
      - "테스트 이름은 조건, 행위, 기대 결과를 드러낸다."
      - "테스트는 하나의 규칙만 검증한다."
    must_not:
      - "테스트 없이 프로덕션 코드를 먼저 수정하지 않는다."
      - "구현 세부사항 또는 private 멤버에 의존하지 않는다."
  green_phase:
    description: "실패 테스트를 통과시키는 최소 구현만 수행한다."
    rules:
      - "현재 실패 테스트를 통과시키는 가장 작은 변경만 허용한다."
      - "기존 테스트 실패가 발생하면 즉시 원인을 확인한다."
    must_not:
      - "미래 요구사항을 예측해 범용 구조를 만들지 않는다."
      - "테스트가 요구하지 않는 기능을 추가하지 않는다."
  refactor_phase:
    description: "모든 테스트가 통과한 뒤 동작을 유지하며 구조를 개선한다."
    rules:
      - "리팩터링 전후 관련 테스트는 모두 통과해야 한다."
      - "중복 제거, 이름 개선, 책임 분리, 의존성 정리를 수행한다."
    must_not:
      - "테스트 실패 상태에서 리팩터링을 계속하지 않는다."
      - "동작 변경과 구조 개선을 한 단계에 섞지 않는다."

testing:
  framework:
    unit: "Google Test"
    approval: "Approval Tests"
    alternatives_allowed: false
  structure:
    - "각 테스트는 Given-When-Then 주석 구조를 사용한다."
    - "Given은 입력, 설정, fixture 상태를 준비한다."
    - "When은 검증 대상 동작을 1회 실행한다."
    - "Then은 관찰 가능한 결과를 검증한다."
  fixture_rules:
    - "공통 준비가 2개 이상의 테스트에서 반복될 때만 test fixture를 사용한다."
    - "fixture는 테스트 간 공유 mutable 상태를 남기지 않는다."
    - "SetUp은 테스트 의도를 숨길 만큼 많은 데이터를 만들지 않는다."
    - "TearDown은 외부 자원을 사용한 테스트에서만 정의한다."
  approval_test_rules:
    - "HTML, CSV, JSON, 대량 텍스트 출력은 Approval Test로 고정한다."
    - "승인 파일 변경은 출력 계약 변경으로 간주한다."
    - "Approval Test는 비결정적 값, 시간, 순서 의존 값을 제거한 뒤 수행한다."
  coverage:
    domain_line: 95
    domain_branch: 90
    boundary_line: 90
    data_line: 85
    contract_tests: 100

forbidden:
  - "std::cout 또는 std::cerr 디버그 출력을 남발하지 않는다."
  - "매직 넘버와 매직 문자열을 하드코딩하지 않는다."
  - "catch(...)를 무분별하게 사용하지 않는다."
  - "헤더 파일에 일반 함수 또는 클래스 메서드 구현을 포함하지 않는다."
  - "전역 mutable 상태를 남용하지 않는다."
  - "using namespace std를 헤더에 작성하지 않는다."
  - "raw pointer 소유권을 명확한 규칙 없이 사용하지 않는다."
  - "new와 delete를 직접 짝지어 자원 수명을 관리하지 않는다."
  - "테스트를 통과시키기 위해 프로덕션 계약을 완화하지 않는다."
  - "레이어를 우회하여 Boundary에서 Entity 내부 규칙을 직접 수정하지 않는다."

file_structure:
  tree: |
    # boundary/  외부 입력, 검증, 출력 변환, 오류 응답
